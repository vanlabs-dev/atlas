# Design: telegram-voice-overhaul

## Context

Atlas speaks to its single operator through two Telegram paths. Inbound
conversation is LLM-generated by the native Hermes gateway (Grok via X
OAuth), whose identity comes from a stock `SOUL.md` plus platform hints.
Outbound operational alerts are deterministic templates in
`telegram/atlas_telegram.py` — no LLM — rendering facts already recorded in
SQLite stores. Both paths are accurate but mechanical: raw fields lead,
jargon shifts between messages, and nothing states meaning or next action.

The operator's voice foundation has three layers, already in daily use:
ADHD-mode layout (answer first, no framing, next action), ASD-STE100
structure for instructions (imperative, one action per sentence, approved
lexicon, warning-before-condition), and Zinsser clarity for prose. Conflict
rule: STE wins instructions, Zinsser wins prose. Sentence-length caps were
considered and **rejected by the operator**: tight by discipline, not by
limit.

Hard constraint from the PRD lineage: accuracy is non-negotiable. Alerts
must keep every figure sourced, escaped, scrub-or-refused, and
de-duplicated; chat must never present unvalidated data as fact (the MV-RI-4
failure class: Grok asserting remembered values as live).

## Goals / Non-Goals

**Goals:**
- One voice foundation covering both paths, with a fixed approved lexicon
  (one concept, one word) and a fixed uncertainty vocabulary.
- Chat: Atlas answers first, stays tight, cites sources, and says "I do not
  know" / "not verified" instead of guessing.
- Alerts: all seven classes get a verdict-led layout — plain-language
  headline, glossed jargon, sourced fact lines, next-action line.
- Accuracy preserved by construction: templates re-render recorded fields
  only; chat honesty enforced by prompt rules and re-tested adversarially.

**Non-Goals:**
- No changes to event detection, watermarks, the delivery ledger, scrubbing,
  scheduling, or alert classes themselves.
- No new event classes, no service-failure class (still deferred).
- No changes to the dashboard (`var/fleet/www`) or mining-triage outputs.
- No sentence-length caps or other numeric prose limits.
- No trading, signing, or wallet capabilities (standing PRD prohibition).

## Decisions

### D1: Canonical voice text lives in the repo; the operator applies it

The voice foundation is authored once in the repo (`telegram/docs/voice.md`
— lexicon, layout rules, uncertainty vocabulary, full SOUL.md text, platform
hint text). Device application follows the established Atlas pattern: the
operator copies it into `~/.hermes/SOUL.md` and `~/.hermes/config.yaml`
(`platform_hints.telegram` append), with the repo's backup convention
(`config.yaml.bak-<change>`). Nothing writes device config from code.
*Alternatives:* code that rewrites device config (rejected — violates the
operator-applies convention); device-only edits (rejected — unversioned,
unreviewable).

### D2: SOUL.md carries the core voice; the platform hint carries mobile-voice rules only

SOUL.md replaces the stock identity: who Atlas is, the voice layers, the
honesty contract, the uncertainty vocabulary. The `platform_hints.telegram`
append holds only what the stock Hermes Telegram hint does NOT already say:
the base hint covers Markdown conversion, media tags, and chunking, so the
append is limited to voice-on-mobile rules: verdict first on a small
screen, short lines, chunk-aware structure. *Alternatives:* hint-only
(rejected: the core voice would not apply to CLI sessions); personalities
(rejected: single-paragraph personas, no layered rules); appending the full
voice in the hint (rejected: duplicates prompt text every turn).

### D3: Lexicon lives in `telegram/config.json`, extended per the wording-map precedent

The config already carries `area_map`, `pallet_map`, and `governs` wording
maps. The lexicon follows that pattern: an approved-terms map (concept →
the one word) and a jargon-gloss map (term → one parenthetical gloss for
first use). The lexicon config is REQUIRED: a missing or incomplete map
fails closed (rendering refuses) rather than falling back to untested code
defaults. Renderers read it; tests assert rendered output conforms, and a
conformance test asserts every config entry exists in the `voice.md`
canon. *Alternative:* a new shared module both chat and alerts read
(rejected — chat is prompt text, alerts are templates; there is no shared
code path to share it through).

### D4: Alert restructuring re-renders recorded fields only — zero new interpolations

Every headline, gloss, and next-action line is built exclusively from values
the stores already record (netuid, share, bar, margin, sources, cooldown
state, spec versions, paths). No renderer fetches, computes, or infers new
facts. This is what makes rewording accuracy-safe by construction.

### D5: Per-class headline templates on the existing render frame

The render frame (`render_html` / `render_plain` with headline, lines,
expandable, trailer, and the shrink loop) already exists and every class
already fills a headline slot. The work is per-class template edits — new
headline wording, gloss-once helper, line regrouping — not a new shared
abstraction. A generic wrapper cannot write a truthful verdict, so each of
the seven classes gets its own headline template with fixed slots (e.g.
gate-crossing: direction, subnet, consequence), driven by the same recorded
fields the fact lines use. Jargon is glossed once per message at first use.

### D6: No sentence caps (operator decision)

STE's 20/25-word limits are dropped. Concision is enforced by Zinsser's
cut-clutter rule and review, not by assertion. Tests check lexicon
conformance and structure (headline present, facts sourced, next-action
present), never word counts.

### D7: Chat accuracy is prompt-enforced and battery-verified

SOUL.md carries the honesty contract: no tool evidence → no number; label
dated data as dated; say "I do not know"; never present remembered values as
live. Acceptance includes re-running the MV-RI-4 adversarial battery
(`hermes/modelval`) against the re-voiced chat on the Pi, extended with 2–3
voice probes (answer-first structure, banned-synonym absence, next-action
presence) so the chat-side lexicon has a named verification. *Alternative:*
trusting the existing retrieval-first machinery without a prompt change
(rejected — that machinery grounds answers it is asked for; the voice change
alters how the model frames everything else).

### D8: The shrink path protects the layout

`render_html`'s degrade order today is: shrink the expandable, drop the
trailer, then drop body lines from the end — which would kill a trailing
next-action line first. The shrink path gains a protection order: expandable
absorbs shrinkage first, body fact lines drop next, the next-action line
drops last, and the headline is never dropped or truncated into.
*Alternative:* fixture-budget-only testing (rejected — real un-fixtured
messages would silently lose exactly the elements this change exists to
add).

### D9: Alert-side uncertainty rides the existing source labels

Renderers never validate at render time, so per-figure `confirmed` tags
would be both false and cluttered. The alert-side realization of the
uncertainty vocabulary is the existing source-label system (provider, chain
RPC, block, commit) plus explicit `dated` / `n/a` markers on stale or absent
elements. Chat keeps the verbal vocabulary (`confirmed` / `dated` /
`not verified` / "I do not know").

## Risks / Trade-offs

- **Prompt change drifts Grok's behavior** (verbosity, tool-use cadence,
  refusal patterns) → full modelval battery re-run before acceptance; keep
  SOUL.md additive in spirit (identity + voice), not a rewrite of tool-use
  enforcement, which already lives in the stable prompt tier.
- **Longer messages vs the 3500-char budget** → headlines replace rather
  than stack on existing lines where possible; per-class rendering tests
  assert the budget with worst-case recorded fixtures; the size guard and
  plain-text fallback are untouched.
- **Voice slides toward casual/cute and erodes alert gravity** → the
  lexicon is fixed and Zinsser's no-clutter rule bars filler; no emoji
  policy change (alert badges stay as-is).
- **Operator application error on device config** → backup-before-edit per
  repo convention; a read-only verification step (diff against canonical
  text) confirms the applied SOUL.md and hint match the repo.
- **Divergence between chat and alert vocabulary over time** → both draw
  from the one canonical `voice.md`; lexicon changes go through this repo's
  change process.

## Migration Plan

1. Land renderer + config + tests via `git pull` on the Pi; run the telegram
   suite (off-device first, then on-device).
2. Operator applies SOUL.md and the platform hint (backups first), restarts
   the gateway (`systemctl --user restart hermes-gateway`).
3. Send one `test --class` alert per class; confirm layout and ledger.
4. Run the MV-RI-4 adversarial battery against live Telegram chat.
5. Rollback: restore `SOUL.md`/config backups and restart the gateway for
   chat; `git checkout` the prior renderer for alerts. No watermarks or
   stores are touched by this change, so rollback is stateless.

## Open Questions

None blocking. (Parked: applying the voice to `mining.html` and triage
outputs later; whether the dashboard header copy adopts the lexicon.)

## NOT in scope

- Dashboard (`var/fleet/www`) and mining-triage outputs: separate surfaces, parked thread.
- New alert classes (incl. service-failure): still deferred per telegram-integration spec.
- Ledger, watermark, dedup, cooldown, and digest behavior: byte-identical by task 2.10.
- `session_reset` config change: long-lived sessions are the operator's standing choice; only a one-time reset after SOUL.md application.
- Sentence-length caps: rejected by the operator.
- Code-generated config lexicon: conformance test chosen over codegen (F1).
- Gateway code: ATLAS-TG-001 untouched; Atlas contributes no gateway code.
- Emoji/badge policy: unchanged.

## What already exists (consumed, not rebuilt)

- `render_html` / `render_plain` (atlas_telegram.py:421,455): headline + lines + expandable + trailer frame with shrink loop and sentinel-safe typography. The change extends this frame; it does not build one.
- Per-class headline slots (atlas_telegram.py:872, 1017, 1190, 1307, 1428, 1620): verdict badges exist; the change re-voices them into plain-language verdicts.
- Config wording maps (`area_map`, `pallet_map`, `governs` in telegram/config.json): the precedent the lexicon maps follow.
- Hermes `platform_hints` config mechanism (verified on device v0.18.2): the built-in lever for the Telegram append.
- `hermes/modelval` battery machinery: runner, scorer, thresholds; the acceptance battery and voice probes reuse it.
- Source labels in fact lines ("shares: TaoSwap panel · bar: chain RPC · block N"): the alert-side confirmation story (D9).
- Suppress-record-never-drop cooldown (atlas_telegram.py:1106-1113): restated in the spec, unchanged.

## Data flow

```
INBOUND CHAT                          OUTBOUND ALERTS
─────────────                         ───────────────
Telegram poll                         stores (repotrack/livedata/
  │                                    fleet/knowledge)
  ▼                                        │ read-only, past watermarks
allowlist (TELEGRAM_ALLOWED_USERS)         ▼
  │                                   per-class renderers
  ▼                                        │ recorded fields ONLY (D4)
session (agent:main:telegram:dm:…)         ▼
  │                                   lexicon + gloss maps (config.json,
  ▼                                        │ required, fail-closed)
system prompt = SOUL.md (voice,            ▼
  honesty, uncertainty vocab)           render_html/render_plain
  + platform_hints.telegram              │ headline → facts(+sources) →
  (mobile-voice rules)                   │ next-action (conditional)
  ▼                                        ▼
Grok (xai-oauth) + tools              shrink path (D8 order)
  │ no tool evidence → no number         ▼
  ▼                                   scrub-or-refuse (unchanged)
format_message → MarkdownV2              ▼
  │                                   HTML send; 400 → plain text once
  ▼                                        ▼
chat                                     ledger (unchanged)
```
